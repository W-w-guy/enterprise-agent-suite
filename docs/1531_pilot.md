# 44/50 非提案业务试点

## 客户原话要什么
「选择一个公司级非提案任务串联知识、编排、审批与评测。」

## 选的任务：月度费用异常核查

不是演示玩具，是真实会发生在财务共享中心的一条链：
知识库口径 → 检出偏离 → 生成通知 → 人工审批 → 投递队列 → 评测打分。

## 六步与审计
`load_policy → detect → draft → approve → deliver → evaluate`，
每一步都往 `audit.jsonl` 追加一条记录（崩溃时可看出断在哪一步）。

## 三个可验证的点

**1) 审批是硬门。** `--no-approve` 时：审批门返回「未审批」，
`queue.jsonl` 根本不生成。不是「生成了但标红」。

**2) 审批后改一个字，立刻失效。** `--tamper` 会在正文后加一句，
哈希不匹配，门拦下并说明「内容已改动：审批哈希 xxxx… 与当前 yyyy… 不一致」。

**3) 坏数据不阻塞。** 缺历史基线的行被跳过并列入「被跳过的数据行」，其余照常检出。

## 已修的缺陷（重要）
初版评测表把「被门拦下」当成通过，导致报告自相矛盾：
审批通过、但评测显示「未审批不投递：未通过」。
现在判的是**「审批结论与投递动作是否一致」**：
门通过却没投递 = 失败（悄悄吞掉），门拦下却投递了 = 失败（门形同虚设）。

## 治理细节（对抗轮补的）

| 场景 | 旧行为 | 现行为 |
|---|---|---|
| 换了责任人，旧批文还在 | 照样放行 | 拦下：「批文人不是当前责任人」 |
| 同一正文被批两次 | 静默取最后一次 | 留 `approval_repeated` 审计事件，能查被批过几次、都是谁 |
| 通知正文 4000 字以上 | 入队，被网关拒 | 入队前就拦住并说明 |

## 边界
规则与阈值从 `policy.json` 读，客户自己改；不含真实财务系统对接。
